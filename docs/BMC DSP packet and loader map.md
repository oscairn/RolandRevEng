# BMC DSP packet and loader map

2026-11-09, extended 2026-11-10. Follow-up to **BMC DSP ISA**, **BMC chips**, and **Fantom-0 research**.
Target: Fantom-0 v1.08, especially Fantom-07; local ZENOLOGY arm64 implementation as a
comparison. This is static interoperability research. No firmware was installed, no
instrument was accessed, and no program has been tested on a BMC.

**Result:** the available evidence now supports a deterministic packet decoder, the
control-word/payload split, explicitly sized coefficient decoding, voice-side image
locations, and a concrete CORE1 program-loading map. It does **not** yet support compiling
an arbitrary C/C++ synth to the render DSPs. Most arithmetic opcodes, scheduling, precision
and resource rules remain unresolved.

The [label-target study](label-target-encoding-study.md) verifies CORE1's counted
reference-record layout and explicit halfword target encoding, including five
parent numeric matches. Actual incoming field ownership and DSP saved-return
semantics remain unresolved; the original voice plans still exclude wrappers.

## 3. Packet grammar and partial opcode map

### Storage and packet lengths

Reverse each complete 4-byte stored word to obtain the logical byte stream. Include
the final storage padding before swapping, then trim to the declared logical length.
Swapping only a partial last word misplaces the last instruction. Logical words are
big-endian; logical program addresses count bytes.

Except for compact forms, the observed packet word count is `header & 0x1f`, including
the header. The following are **single-word** packets:

| Word | Established fact | Remaining uncertainty |
|---|---|---|
| `0001` | NOP: stock `StackFillDspProgNop` writes repeated `0x00010001` | Exact issue/latency behavior |
| `001f` | Compact one-word form; consuming 31 words is wrong | Likely an extended idle/NOP count, but duration is unmeasured |

Header bit 5 is clear in every correctly parsed observed packet. Five bits suffice
for observed lengths; a six-bit length field cannot be distinguished from these files.
The tool rejects bit 5 and compact values other than `0001`/`001f` until evidence exists.
It does not silently treat unknown bytes as literals.

The old low-**nibble** rule fails on real long packets. `8fd1`, for example, occupies
17 words. Earlier scratchpad results claiming that all lengths were four bits long
were circular: the parser imposed that rule and then counted its own output.

### Control-word count

For noncompact packets, let `H` be the header:

```text
if H has bit 15 set: control_count = 5 + ((H >> 6) & 3)
otherwise:          control_count = bit_length(H >> 11)
packet = header, control_count 16-bit control words, remaining payload bytes
```

Examples: `0c03` has 1 control word, `1e05` 2, `3e07` 3, `7809` 4,
`b809` 5, `b84b` 6, `b88d` 7 and `8fd1` 8. Compact forms have zero control words.
This split passes the independent relocation/default-address checks above. Remaining
header flags and their relationship to issue slots and operand encoding are unresolved.

All packet starts are even byte offsets. Odd coefficient addresses are **inside** the
payload; they do not shift the next packet onto an odd byte boundary. The former
byte-space DP parser's odd-start theory was an artifact of incorrect segmentation.

### Indexed transfers

In the control area, words `NFE(2i)` refer to payload word `i`, counted from immediately
after all control words. Thus low bits `FE0`, `FE2`, … `FEE` select payload offsets
0, 2, … 14 bytes. This is not the ordinal position in a run of apparent registers.

The high nibble is a transfer operation/port selector. The following behavior is
supported by paired native examples; the complete port/register model is still inferred.
EH independently loads a live coefficient through port 1, so coefficient/data roles
below describe common uses rather than exclusive register types:

| Control form | Working interpretation | Evidence strength |
|---|---|---|
| `0FEk`, `4FEk` | Load the two main data paths from the indexed memory operand | Strong in FETDRIVE/TS808 input and reload sequences |
| `1FEk`/`2FEk`, `5FEk`/`6FEk` | Additional data inputs in the two arithmetic paths | Native delay/filter reads; precise register names not recovered |
| `3FEk`, `7FEk` | Coefficient inputs in the two paths | Native live-coefficient reads, including `C0xx` payload operands |
| `8FEk`, `CFEk` | Store the two main results | Native DM stores and output routing |
| Remaining `9/A/B/D/E/F FEk` | Other transfer ports; bit 3 of the nibble suggests store direction | Inferred; no complete semantic table yet |

For example, FETDRIVE's output packet at relative `0x1ba` is:

```text
3d06 | 00f8 8fe0 cfe2 | 2018 2019
```

Three controls, two payload words: store main result A to IO `2018`, B to IO `2019`,
plus the `00f8` control. The meaning of `00f8` and its scheduling effect need proof.
Within the stock MFX context, `2016/2017` are input slots and `2018/2019` output slots;
these are not proven physical TDM slot numbers.
The kernel follow-up traces them to shared native routing storage, including fallback
output values, and shows different operands in other instances and firmware.
`SetMuteMode` also scans the labeled first packet and rewrites its `ff70/ff71`
control. Those values are mutable mute state in this context, not a universal fixed
entry/exit wrapper; the hardware gate behavior remains unobserved.

The transfer-space follow-up refines the memory tags. Tag-0 accesses use one native
circular data path; the resolved tag-2 accesses use another path and also wrap with
`& 0x7ff`. Stock MFX `2016..2019` have contextual input/output roles, but this does
not make tag 2 globally host IO. Tag 4 accesses a separate CBMCDrm-backed direct/window
double-array path without that mask; it is not established as coefficient RAM. Tag-C
live coefficients use distinct `0x48`-stride records and float loads at record `+0x28`.
These findings describe the native model; the complete hardware-space map remains open.
Literals and operation extensions can contain the same bit patterns as addresses.
Only interpret a word in its decoded role. See [the provenance study](transfer-spaces-study.md).

### Arithmetic: a useful narrow start

Words previously called `04xx/45xx` "modifiers" occupy actual **control-word** slots.
Their arithmetic role can be studied directly now that boundaries are known.

FETDRIVE's final gain sequence, compared with native `VSubProc` at `0x2f7de4`:

```text
0196: 2e05 | 0403 4503 3fe0 | c000
01a0: 1503 | 0403 4503      |
01a6: 1e05 | 8fe0 cfe2      | 0019 001a
01b0: 1e05 | 0fe0 4fe2      | 0019 001a
01ba: 3d06 | 00f8 8fe0 cfe2 | 2018 2019
```

Native code multiplies left/right by the previously read slot 4 coefficient, then
left/right by slot 0, then writes/reloads DM `0x19/0x1a` and writes outputs. The subsequent bounded native def/use study verifies the corresponding two gain
factors on both channels in 12 effect tails, including asymmetric selectors and EH's
port-1 gain. This strengthens the `0403`/`4503` multiply interpretation.
TS808's opening gain chain also fits that interpretation;
`0407`/`4507` fit use of the other coefficient input there. Exact operand bitfields,
wrap/saturation and pipeline timing are **not** proved by that fit.

`080b` and `490b` in the preceding FETDRIVE dry/wet stage are candidates for the paired
mix/MAC operations when considered without their extension/header context. The follow-up
expression-level check establishes the narrower `080b/13c0` and `490b/53c0` forms in the
documented contexts against FETDRIVE and LINEDRIVE. It does not generalize to other
extensions or establish finite-precision behavior. In particular, header `2b0a` is not
itself an ALU mnemonic: a packet can contain several controls and operands.

The retained native operand dumps are `evidence/SIM_MFX_FETDRIVE.native_ops.txt` and
`evidence/SIM_MFX_TS808.native_ops.txt`. Their constructor/address tracing is heuristic;
address aliases and compiler scheduling prevent treating every annotated access as a
one-to-one execution trace.

## 4. Literal widths and native-default differences

`CBmcDspDrv::WriteLiteralFloat/Fixed/Raw` explicitly accept widths **2, 3 or 4 bytes**.
`WriteLiteralRaw` at bmc0 `0x0112f528` checks `(width - 2) < 3` using unsigned comparison.
The float variant at `0x0112ff4e` performs the same check. Thus a leading byte `30` followed
by zeros does not establish a 1-byte literal. Width must come from the instruction's
operand description or `_CoefSym` record, not whichever width happens to fit the value.

For width `n`, first byte `s ee mmmmm` and remaining bytes extending the magnitude:

```text
magnitude = big_endian_bytes & ((1 << (8*n - 3)) - 1)
value = (-1 if s else +1) * magnitude * 2**(-24 + 4*ee + 8*(3-n))
```

| Width | Magnitude bits | Scale for `ee = 0,1,2,3` |
|---|---:|---|
| 2 | 13 | 2^-16, 2^-12, 2^-8, 2^-4 |
| 3 | 21 | 2^-24, 2^-20, 2^-16, 2^-12 |
| 4 | 29 | 2^-32, 2^-28, 2^-24, 2^-20 |

The representable magnitude limit approaches 512 at every width; width controls
precision. The decoder implements all three forms. Examples: `30 00` = 1,
`2f e0 00` = 0.9921875, `50 00 00` = 16, `19 99 99 99` is a 4-byte approximation to 0.1.

Scanning adjacent symbol candidates supplies tentative widths for 2,684 native defaults:
72 width-2, 2,174 width-3, 438 width-4. Of these, 2,134 match exactly and another 549
are within one encoded LSB. This explains much of the earlier apparent revision drift.
790 defaults still lack an unambiguous candidate width in the bounded scan. This search
does not prove that a matching record belongs to the selected class; candidate counts
are retained for reproducibility, not reported as owner-proven width metadata.

The old width-candidate mismatch is `SIM_MFX_GASSPH`, relative `0x2a8`, candidate width 4,
native `0.998046875`, image `0.9980475269258022` (175 LSB difference). Its symbol is at
ZENOLOGY file offset `0x827cac`. The expanded operand decoder instead predicts width 3
at that location, independently of numeric fitting; it decodes to the native value
exactly. The candidate lies next to MS_COMP, whose own width-4 zero at the same relative
address fits it. A neighboring table association is the strong explanation, not
evidence of revision drift. The conflict remains explicit until symbol ownership is
fully traced; see [the detailed analysis](header-fields-study.md).
The much larger native value 646.1 mentioned in the older note still
cannot be represented by this format and must not be used to infer an unlimited range.

`evidence/coefficient_widths.json` retains every matched symbol position, width, native
value, decoded value and quantum so that a future assembler can audit the claim.

The subsequent [operand-field study](header-fields-study.md) independently recovers
the encoded reference for its supported ALU families: high two bits select register,
2-, 3- or 4-byte literal; low four bits select the register index or a byte offset
inside the common operand pool. Long operations use one such field in the base word
and two in an extension word. The expanded mixed layouts check 2,234 adjacent metadata
candidates, retaining the single conflict above. No width is selected by trying numeric
fits. Special operations, miscellaneous families and other transfer windows remain
explicitly unsupported.

## 5. CORE1 executable and scatter map

All offsets in the firmware tables below are into the **payload after stripping the
32-byte C1A container header**. Add `0x20` for offsets in `*_C1A_up.bin`.

Both builds have an ARMCC scatter bootstrap at payload `0x3ffe0`, mapped to `0x61000000`:

```text
ITCM/startup:   runtime 0x01100000 + payload_offset, for offset < 0x3ffe0
ERAM image:    runtime 0x61000000 + payload_offset - 0x3ffe0
```

The vector reset code calls FPU/low-level initialization and branches to Thumb address
`0x61000001`. The ERAM startup reads relative table bounds at `0x61000034`, walks 16-byte
records, and dispatches copy/decompress/zero handlers. Thus this map follows executable
startup logic and pointer references, not just a guess from `0x61xxxxxx` constants.

### Program-list ABI

Observed layouts differ between CORE1 and the desktop plugin:

| Record | CORE1 | ZENOLOGY arm64 |
|---|---|---|
| Program-list header | bytes `type, DSP index, segment count, padding`; pointer at +4; 8-byte record | u32 type at +0; DSP byte +4; count byte +5; pointer +8; 16-byte record |
| Segment | u32 base, length, capacity, data pointer; stride 16 | u32 base, length, capacity, padding; pointer +16; stride 24 |

Type 0 selects render program lists; type 1 is handled by the separate DRAM-IO path.
`0x205` in the old desktop parser contains DSP index 5 and segment count 2. It is not
evidence of generic permission/relocation flags. The ABI difference may involve enum
representation, but its C++ declaration was not recovered.

also exist, well beyond the small MFX segment capacities. `0x800` was never a universal
per-DSP instruction or cycle limit.

## 6. Concrete DSP loading interface

The following function addresses and tables are for **bmc0 v1.08 commit 947de6711 only**.
For a callable Cortex-M function pointer, set bit 0. Values shown in the table are code
addresses with bit 0 clear. These are disassembly results, not a tested injection API.

| Function | Address | Recovered behavior |
|---|---|---|
| `GetDspProgAdrs` | `0112f92a` | Returns the aperture below plus a byte address; checks DSP index and even address |
| `StackWriteDspProg` | `0112f582` | `r0=dsp`, `r1=byte address`, `r2=byte count`, `r3=stored-word source`; even address/count; direct copy or queued DMA |
| DMA completion helper | `0112f6a4` | Starts queued transfer and, for nonzero argument, waits for completion; name is inferred |
| `WriteLiteralRaw` | `0112f528` | Writes a width/address command and a raw value via the DSP's literal port |
| `WriteLiteralFloat` | `0112ff4e` | Same address/width command; writes float from `s0` to the hardware conversion port |
| `WriteDspProgAllImpl` | `01131c4e` | Walks the CORE1 program-list records, calls `StackWriteDspProg` per segment, optionally completes DMA |
| `SetExeMode` | `01130b6c` | Packs event, mode and start/address argument into a per-DSP control register |
| `GetExeMode` | `01130be6` | Reads bits 25:24 of that register |

`StackWriteDspProg` is not an instruction translator. For aligned bulk data it copies
the supplied 32-bit storage words unchanged, either with a CPU loop or
`DSP_listed_memcpy` at `0x0112f290`. It uses the raw literal port for halfword edges.
Therefore the packets being decoded are genuinely what the stock loader writes to
program RAM, subject to hardware interpretation, rather than a desktop-only format.

The driver routines above use DSP index in `r0`, rather than a hidden C++ `this` pointer.
The manager routine does use an object pointer. Do not treat their calling conventions
as interchangeable. The float store from `s0` establishes a VFP argument requirement;
an injected stub must preserve the actual firmware ABI and task context.

### Apertures and ports

| DSP index | Program RAM | Float literal port | Fixed literal port | Raw literal port | Execution control |
|---:|---|---|---|---|---|
| 0 | `41480000` | `41104400` | `41104600` | `41104700` | `41104310` |
| 1 | `41580000` | `41105400` | `41105600` | `41105700` | `41105310` |
| 2 | `41680000` | `41106400` | `41106600` | `41106700` | `41106310` |
| 3 | `41780000` | `41107400` | `41107600` | `41107700` | `41107310` |
| 4 | `41880000` | `41108400` | `41108600` | `41108700` | `41108310` |
| 5 | `41980000` | `41109400` | `41109600` | `41109700` | `41109310` |
| 6/MDSP | `41260000` | `41102400` | `41102600` | `41102700` | `41102310` |

For literal ports, the command at port+0 is `(width << 28) | (address & 0x7ffff)`;
port+4 carries the value. Float writes pass IEEE float bits to the hardware conversion
port; host software need not invent a rounding policy for a stock runtime write.
Raw read waits on bit 31 of `0x41100008`; writes finish with a read of `0x41100000`.
The raw writer's alignment flag shifts a right-justified value by `8*(4-width)`.

DRAM-IO has separate program apertures, banks at `41440000/41444000` for DSP0, each
increasing by `0x100000` through DSP5. Its instruction format is **not** the render
packet format; RAMCLR belongs here. An effect needing ERAM cannot ignore this path.

Execution control packs `event << 28 | mode << 24 | argument`. The stock checks require
mode < 3, event < 9, and an even 16-bit argument; DSP4/5 explicitly reject mode 2.
What the enum values and events do must still be established. This is not sufficient
evidence for a safe stop/start sequence. Queued DMA tracks state 0/1/2 and completion
bit 4 in bmc0 SRAM; arbitrary writes racing the stock manager can corrupt a running graph.

These addresses are in the **BMC CORE1** address space. Mapping the same numbers through
the i.MX8M's `/dev/mem` does not establish access to them. The bridge follow-up finds
a CORE-local SysEx MMIO service based at `0x41100000`, with writes below offset
`0x01000000`; all seven program apertures lie within it. Its host forwarding route,
manager coordination and safe use remain unproved. Its read helper reserves `0x50`
stack bytes but can emit 139 bytes at the allowed count of 64. Address overlap alone
does not supply a safe loader or an ARM-code installation route for a resident agent.

The stock manager's all-program uploader does not read segment capacity. Segmented
uploaders instead check manager-owned capacities, with different destination rules
for ordinary versus unique segments. FETDRIVE's five list entries belong to DSP4,
DSP5 and DSP1 contexts despite a list-header DSP byte of 1. The read-only
`kernel_abi.py` inspector validates those reservations and explicitly reports
`execution_ready: false`; neither it nor the emitter relocates a complete graph.

## 7. CORE0 and new public work

The older statement that no public BMC RE exists is outdated. Relevant primary work:

- [edco/mc-101-re](https://github.com/edco/mc-101-re): the author's MC-101 CORE1 hook,
  memory/ROM dumping tools and CORE0 modification workflow. This is an independent
  demonstration on a related BMC instrument, not a Fantom acceptance test.
- [Its CORE0 decryptor](https://github.com/edco/mc-101-re/blob/main/tools/decrypt_c0a.py)
  describes 3-key 3DES ECB, bus-word conversion and a boot-ROM key table selected by the
  container's index. It needs a locally supplied boot-ROM dump; the code does not provide
  the ROM or the keys.
- [soobrosa/mc101-firmware-re](https://github.com/soobrosa/mc101-firmware-re) supplies
  independent MC-101 protocol/parameter analysis. Its older memory-map statements are
  not a substitute for the Fantom startup map recovered above.

The local Fantom C0A headers can now be read against that documented layout:

| Field | bmc0 | bmc1 |
|---|---|---|
| Encrypted payload begins | `0x60` | `0x60` |
| Payload size | `0x174eb0` | `0x16f070` |
| Load destination | `0x60000000` | `0x60000000` |
| Crypto control at `0x54` | `0xb6020001` | `0xb6020001` |
| Enabled / mode / key index | 1 / 2 / `0xb6` | 1 / 2 / `0xb6` |

Thus the earlier `0x48` ciphertext boundary was wrong: that word is a load destination
inside the plaintext header. Mode/index match the public MC-101 implementation exactly.
**Inference:** the same 3DES/control layout is a strong candidate for Fantom CORE0.
No local decryption or key-table identity has been verified; a matching index alone
does not prove identical key material or a common silicon revision.

The later [six-image comparison](core0-ciphertext-and-key-location.md) goes beyond
matching indices: it finds 14,335 distinct nontrivial eight-byte payload blocks
shared between Fantom bmc0/bmc1, and 8,124–15,985 shared with each other model.
These bounded counts replace the earlier 14,351 estimate. The documented MC-101
ROM table would put entry B6 at `012034c0`, but this is a BMC-side candidate, not
an i.MX `/dev/mem` address or an established Fantom read route. No actual key
candidate or decrypted CORE0 image was recovered.

Do not spend effort on blind DES/Blowfish/XTEA guessing before checking the boot-ROM
route. Repeated ECB blocks and known plaintext do not reveal a strong cipher's key by
themselves. The old claim "one revealed block is one key reveal" and its cracking-time
estimates were unsupported. The MC-101 hook's product addresses, container checksums
and flash instructions also cannot be copied to the Fantom without validation.

## 8. What a custom engine still needs

The practical architecture remains: i.MX8M for UI, patch control and larger graph
management; CORE1 for the bridge and DSP resource management; render DSPs for compatible
sample/voice/filter/effect kernels. CORE1 is an ARM CPU, and the render DSPs have this
separate ISA. Building an ARM binary for CORE1 does not offload an existing ARM/CLAP
engine to the render array.

The next work should proceed in this order:

1. **Complete arithmetic decoding offline.** Lift the paired native routines into
   expressions between packet payload anchors. Start with multiply, multiply-add,
   state write, saturation/wrap and simple coefficient loads. Separate header/layout
   knowledge from ALU meaning; do not label hundreds of headers as solved opcodes.
2. **Recover entry and ownership.** Identify a Fantom-specific CORE1 execution hook or
   proved external service path and safe task entry. Stock reservation descriptors,
   mute/load ordering and the check/set exclusion byte are now mapped, but full state
   initialization, scheduling, stop/start events and peer forwarding remain open.
   An offline unsigned-looking image does not prove that the
   updater accepts it or that a bad image is recoverable.
3. **Read back before constructing a new program.** With a verified resident route,
   compare a stock segment's runtime RAM with its stored bytes and confirm coefficient
   writes through stock APIs. Account for live writes and inter-instance relocation.
4. **Establish a tiny kernel ABI and timing.** In an owned, muted test region, validate
   pass-through, zero, gain, impulse delay and a one-state filter against the native
   model. Measure issue budget, register readiness, state updates, clipping and noise.
   Existing `2016..2019` effect slots are a contextual lead, not a universal audio ABI.
5. **Map host audio and complete the control bridge.** Normal application BMC IPC has
   a statically traced `/dev/ttyGS0` path; the missing peer must connect its outer
   envelopes and replies to CORE1's rings/services. An owned decrypted peer image or
   existing bidirectional stream/ring capture is the next concrete evidence needed.
   Preserve the stock instance's recovered shared IO assignments and determine both BMCs' clock/routing roles,
   and how custom engine buffers enter and leave that context. ERAM kernels also need
   the DRAM-IO scheduler/FIFO contract.
6. **Extend the constrained emitter into an engine backend.** The two independently
   checked mix/filter fragment templates already emit control/payload records and
   preserve their observed ordering. A general backend must additionally handle
   remaining instruction forms, labels/relocations, initial state, resource bounds and a
   proven schedule. The existing fragments are not complete executable kernels;
   translating arbitrary existing synth C++ is not yet justified.

Stock-program reparameterization is closer than a new engine, because CORE1 already
has literal conversion and live coefficient APIs. This pass does not demonstrate either
path on hardware. Physical recovery, update acceptance, numerical accuracy and timing
remain material limits on claiming a working custom BMC engine.

The reviewed offline probe design therefore retains an entire stock effect instance
and its parent graph, beginning with master-zero, pass-through and gain calculations
in verified finite state. It requires proven entry/recovery, manager task/identity,
quiescence, program/parameter readback and routing capture before any execution.
Normal ttyGS0 IPC can contend with the prepared shell payloads; neither was changed
or used. At the original checkpoint no Qwen output was obtained because command
networking blocked the configured endpoint. Later reviewed network executions
returned bounded Qwen drafts; their checks and rejected claims are in the work log.

## Reproduction and scope

Run the commands in the project README. `prepare_zenology.py` regenerates the same thin
image and `extract_zenology.py` reproduces the paired metadata from the installed plugin;
the old scratchpad pickle is no longer a required input. The tools use Python and the
already installed Capstone, plus Apple's export/demangle utilities for preparation.

REA's CLI was attempted, but Hopper returned `provider_unavailable` at launch. No client
configuration was changed. Disassembly and structural findings above are from ordinary
file reads and Capstone, **not** successful REA decompilation or runtime Evidence.
No production engine, update package or device state was changed.
